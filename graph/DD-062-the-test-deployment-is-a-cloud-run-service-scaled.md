# DD-062: The test deployment is a Cloud Run service scaled to zero with a Neon database, tested by a live suite run on demand

## Decision

The project's test deployment ([SRC-266](SRC-266-the-test-deployment-runs-on-gcp-and-neon-set-up-b.md), [SRC-270](SRC-270-the-test-deployment-runs-on-cloud-run-scaled-to-z.md)) is described by Terraform scripts in the repository, which the owner applies from their own machine. They create:

- **The service:** one Cloud Run service running the published application image ([DD-040](DD-040-the-tool-ships-as-one-application-image-run-with-p.md)), scaled to zero and to at most one instance. It is reached at the HTTPS address Cloud Run gives it, with Cloud Run's own certificate, and anyone may call it: the tool checks every call itself. Its CPU stays allocated for as long as an instance is up, not only during a request, so that the re-check timer ([SC-024](SC-024-re-check-timer.md)) runs and a webhook delivery answered at once is still handled afterwards. An instance is up while calls come in, as they do throughout a test run, and for a while after; between runs nothing runs.
- **The image:** Cloud Run cannot pull from the GitHub Container Registry, so an Artifact Registry repository in the same project proxies `ghcr.io` and keeps a copy of the image. The image is private, so the proxy signs in with a classic personal access token of the owner's that has only the `read:packages` scope ([SRC-271](SRC-271-the-test-deployment-pulls-the-private-image-with-a.md)). The proxy keeps serving a tag as it first fetched it, so Terraform looks up, at each plan, the version the tag points to on the GitHub Container Registry and gives the service that version by its digest: applying the scripts again updates the tool to the latest image.
- **The database:** a Neon project on Neon's free plan, whose pooled address is the tool's `database.url` and whose direct address is its `database.directUrl` ([FR-177](FR-177-use-the-postgresql-database-given-in-the-configura.md), [DD-059](DD-059-settings-come-from-a-yaml-file-overridable-by-envi.md)).
- **The settings and secrets:** the GitHub App's private key, which the tool reads from a file, and the registry token are kept in Secret Manager; the key is given to the service as a mounted file. The other settings (the database addresses, the App's id, the Projects token, the webhook secret, the first system admin) are the service's environment variables, which only the Google Cloud project's own users can read. Terraform generates the first system admin's password ([SRC-269](SRC-269-terraform-creates-the-admin-password-and-writes-t.md)) and the webhook secret itself. Terraform's state holds every secret, so the state stays on the owner's machine.
- **GitHub access** ([SRC-267](SRC-267-the-test-deployment-reaches-github-through-an-app.md), [SRC-295](SRC-295-the-test-bed-is-under-a-github-account-of-its-own.md), [DD-060](DD-060-a-github-function-is-given-an-app-or-a-personal-ac.md)): the GitHub App reads and writes issues (`readIssues`, `writeIssues`), so the tool's issues, comments and reverts show as the App's. A classic personal access token reads the Projects status field (`projectsStatus`): the test repository and its Project are under csillagu-alt, a user account made only for the tests, and neither a GitHub App nor a fine-grained token can read a Project owned by a user account. csillagu-alt makes that token, so it reaches only the test bed.
- **The webhook** ([SRC-267](SRC-267-the-test-deployment-reaches-github-through-an-app.md)): Terraform sets up a webhook on the test repository, pointed at the tool's webhook endpoint ([SC-105](SC-105-github-webhook-endpoint.md)), with the events the tool takes in from a repository (`issues`, `sub_issues`, `issue_dependencies`) and the secret Terraform generated, given to the tool as `github.webhookSecret`. GitHub sends no webhook for a Project owned by a user, so a change to the status field reaches the tool only at its re-check, which is 2 minutes on this deployment unless set otherwise, so that a test does not wait an hour.
- **The `live` environment** ([SRC-269](SRC-269-terraform-creates-the-admin-password-and-writes-t.md)): Terraform creates the `live` GitHub environment of csillagu/cold-seance and writes into it what the live suite needs: the deployment's address, the first system admin's name and password, the test repository, the Project and its status field, the time zone, the wait, and the suite's two tokens. The secrets among them are environment secrets; the rest are environment variables. The environment has the owner as its required reviewer, so no job runs with its secrets until the owner approves that run ([SRC-296](SRC-296-the-live-tests-run-in-ci-on-every-pull-request-each.md)).

The live test suite ([SRC-264](SRC-264-the-github-side-is-tested-against-a-real-github-re.md)) runs against that deployment, through its REST API, and against a test repository under csillagu-alt, the owner's account made only for the tests, with the App installed on it and a Project with a status field. It signs in as the deployment's first system admin. It acts on GitHub as the owner of a fine-grained personal access token of its own on the test repository, standing for the GitHub users the test cases name, and sets the Project's status field with the classic token the deployment reads it with. Each of its tests carries the id of the test case whose GitHub steps it runs, as the other tests do. Since the deployment is not fresh, each run makes its own project, named after the run, and its own tasks and issues. When it ends, it removes the repository from the run's projects, then deletes the issues and milestones it made on GitHub. The projects stay, since the tool has no way to delete a project; the instance is dedicated to these tests ([SRC-266](SRC-266-the-test-deployment-runs-on-gcp-and-neon-set-up-b.md)). The suite runs from the owner's machine with one command, and from a GitHub Actions workflow started by hand, which takes its settings from the `live` environment.

## Alternatives considered

- For running the tool: one `e2-micro` virtual machine of Google Cloud's free tier, with Caddy, Let's Encrypt and sslip.io for HTTPS, which Claude first chose and the owner replaced with Cloud Run ([SRC-270](SRC-270-the-test-deployment-runs-on-cloud-run-scaled-to-z.md)); the same machine with an address that changes at each start; Cloud Run with one instance always running (billed for each hour it runs); Fly.io, which the owner first chose and then replaced with GCP; a GKE cluster.
- For the CPU: allocated only during requests, which costs less per instance but stops the re-check timer and the handling of a webhook delivery after it is answered.
- For the image: making the GitHub package public (the owner chose a token); publishing the image to Artifact Registry from CI, which would give CI credentials to Google Cloud.
- For the database: Cloud SQL (billed); PostgreSQL in a container beside the tool.
- For the settings: every secret in Secret Manager, which is billed beyond six secret versions.
- For the functions: the App for every function, which cannot read a user's Project; a token for every function, which leaves the App out although the owner asked for it.
- For the webhook: the GitHub App's own webhook, whose address and secret are set by hand on the App's page, since the App is registered by hand ([DD-058](DD-058-github-access-uses-apps-registered-by-hand-with-op.md)).
- For the test repository: a GitHub organization of its own, where fine-grained tokens and the App reach the Project and Project changes are sent as webhooks (the owner first chose to stay under csillagu, then moved the test bed to an account of its own, csillagu-alt); fine-grained tokens only under csillagu, leaving the status field untested.
- For the suite's Project access: a second classic token of its own, apart from the deployment's.
- For the `live` environment: Terraform's outputs only, copied into the environment by hand (the owner chose that Terraform writes them).
- For the tests: against a server the test run starts itself (the owner chose the deployment).

## Rationale

The owner asked for whatever is cheaper or free ([SRC-266](SRC-266-the-test-deployment-runs-on-gcp-and-neon-set-up-b.md)) and chose Cloud Run scaled to zero over a virtual machine whose static address is billed all month ([SRC-270](SRC-270-the-test-deployment-runs-on-cloud-run-scaled-to-z.md)). The deployment is used only during test runs, and Cloud Run runs, and bills, only while it is called. Now that the deployment has webhooks, it need not run all the time to see changes made on GitHub: during a run the suite's own calls keep an instance up, and the re-check runs then. Its address and certificate are Cloud Run's and do not change, so the webhook and the `live` environment never need updating. Neon's database sleeps whenever the service does. At most one instance keeps one re-check timer and bounds the cost.

Secret Manager is needed for the App's key, which the tool reads from a file, and for the registry token, which the proxy reads from there; the other settings are environment variables, which cost nothing.

The App for issues and a token for the Projects status field is the one split that uses both, as the owner asked, and works on a user-owned Project; that token must be classic, as the owner chose. A repository webhook can be created by Terraform, so the webhook secret is generated, given to the tool and set on GitHub in one apply, with nothing copied by hand; the App's webhook cannot be set by Terraform. The suite sets the status field with the deployment's classic token so that the owner keeps one classic token for Projects, not two. A short re-check interval stands in for the Project webhooks GitHub does not send for a user's Project.

A run's own project keeps its tasks apart from earlier runs', on a deployment that is not fresh. Removing the repository from the project before deleting its issues keeps the tool from recreating them, as it would recreate a linked issue deleted on GitHub ([FR-136](FR-136-treat-a-linked-issue-deleted-on-github-as-closed.md)).

## Trade-offs

- Between runs nothing runs: a webhook delivery that starts an instance waits for the tool to start, and GitHub gives up on a delivery after 10 seconds; a change to the status field made between runs is seen only at the next run's re-check.
- The first call of a run waits for the tool to start.
- Each plan reads the registry over the network, so planning needs the registry token and the GitHub Container Registry to answer.
- There is no shell on the service: its logs are read in Cloud Logging.
- Each run leaves a project behind in the tool.
- The test cases ask for a fresh deployment; on this one, each test sees what earlier runs left, in projects of their own.
- The suite waits for the re-check after each change it makes to the status field, so those tests take minutes, not seconds.
- The deployment's classic Projects token is given the `project` scope, which writes Projects, although the deployment only reads them.
- The tests of the App's own webhook are not run live: its deliveries are checked by the integration tests only.

## Risks

- Cloud Run's free tier, Artifact Registry's free storage and Secret Manager's free secret versions bound the cost only while they last; their terms may change, and an instance kept up by calls, such as a scanner's, is billed past them.
- Whether Artifact Registry's proxy signs in to the GitHub Container Registry with a classic token is not tested before the first apply.
- A re-check every 2 minutes keeps Neon's compute awake while an instance is up.
- Terraform's state holds every secret in plain text. Lost or shared, it gives them away.
- Terraform needs a GitHub token of csillagu's that can write csillagu/cold-seance's environments and secrets, and one of csillagu-alt's that can write the test repository's webhooks: a collaborator cannot manage the webhooks of a repository owned by a user.
- The classic tokens can do on GitHub what their owner can within their scopes, on every repository and Project their account reaches: the Projects token, csillagu-alt's, reaches the test bed only; the registry token, csillagu's, reads every package csillagu reaches. The Projects token, kept as an environment secret, reaches any workflow run in the `live` environment that the owner approves.
- Which fine-grained permission GitHub requires to delete an issue was not found in GitHub's documentation; the clean-up may fail with a token that lacks it.
