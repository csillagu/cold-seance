# DD-062: The test deployment is one free-tier GCP VM with a Neon database, tested by a live suite run on demand

## Decision

The project's test deployment ([SRC-266](SRC-266-the-test-deployment-runs-on-gcp-and-neon-set-up-b.md)) is described by Terraform scripts in the repository, which the owner applies from their own machine. They create:

- **The machine:** one Compute Engine `e2-micro` virtual machine, the size Google Cloud's free tier covers, in a region the free tier covers, on Google's Container-Optimized OS. At each start it pulls the published application image ([DD-040](DD-040-the-tool-ships-as-one-application-image-run-with-p.md)) and runs it, so restarting the machine or its service updates the tool to the latest image. The tool keeps running between test runs, so that webhook deliveries reach it and its re-check ([SC-024](SC-024-re-check-timer.md)) runs.
- **HTTPS:** a Caddy container in front of the tool takes a certificate from Let's Encrypt for the machine's host name and passes requests on to the tool. The host name is a domain the owner gives, or, if none is given, the machine's address under sslip.io. Only ports 80 and 443 are open to the internet.
- **The database:** a Neon project on Neon's free plan, whose pooled address is the tool's `database.url` and whose direct address is its `database.directUrl` ([FR-177](FR-177-use-the-postgresql-database-given-in-the-configura.md), [DD-059](DD-059-settings-come-from-a-yaml-file-overridable-by-envi.md)).
- **The settings and secrets** (the database addresses, the GitHub App's id and key, the personal access token, the webhook secret, the first system admin) are given to the machine as instance metadata, which only the Google Cloud project's own users can read. The machine reads them again each time it starts the tool. Terraform generates the first system admin's password ([SRC-269](SRC-269-terraform-creates-the-admin-password-and-writes-t.md)) and the webhook secret itself. Terraform's state holds every secret, so the state stays on the owner's machine.
- **GitHub access** ([SRC-267](SRC-267-the-test-deployment-reaches-github-through-an-app.md), [SRC-268](SRC-268-the-owner-s-tokens-are-fine-grained-except-a-clas.md), [DD-060](DD-060-a-github-function-is-given-an-app-or-a-personal-ac.md)): the GitHub App reads and writes issues (`readIssues`, `writeIssues`), so the tool's issues, comments and reverts show as the App's. A classic personal access token reads the Projects status field (`projectsStatus`): the test repository and its Project stay under csillagu, and neither a GitHub App nor a fine-grained token can read a Project owned by a user account.
- **The webhook** ([SRC-267](SRC-267-the-test-deployment-reaches-github-through-an-app.md)): Terraform sets up a webhook on the test repository, pointed at the tool's webhook endpoint ([SC-105](SC-105-github-webhook-endpoint.md)), with the events the tool takes in from a repository (`issues`, `sub_issues`, `issue_dependencies`) and the secret Terraform generated, given to the tool as `github.webhookSecret`. GitHub sends no webhook for a Project owned by a user, so a change to the status field still reaches the tool only at its re-check, which is 2 minutes on this deployment unless set otherwise, so that a test does not wait an hour.
- **The `live` environment** ([SRC-269](SRC-269-terraform-creates-the-admin-password-and-writes-t.md)): Terraform creates the `live` GitHub environment of csillagu/cold-seance and writes into it what the live suite needs: the deployment's address, the first system admin's name and password, the test repository, the Project and its status field, the time zone, the wait, and the suite's two tokens. The secrets among them are environment secrets; the rest are environment variables.
- **Stopping:** a Terraform setting stops the machine between test runs and starts it again.

The live test suite ([SRC-264](SRC-264-the-github-side-is-tested-against-a-real-github-re.md)) runs against that deployment, through its REST API, and against a test repository under csillagu, created by the owner, with the App installed on it and a Project with a status field. It signs in as the deployment's first system admin. It acts on GitHub as the owner of a fine-grained personal access token of its own on the test repository, standing for the GitHub users the test cases name, and sets the Project's status field with the classic token the deployment reads it with. Each of its tests carries the id of the test case whose GitHub steps it runs, as the other tests do. Since the deployment is not fresh, each run makes its own project, named after the run, and its own tasks and issues. When it ends, it removes the repository from the run's projects, then deletes the issues and milestones it made on GitHub. The projects stay, since the tool has no way to delete a project; the instance is dedicated to these tests ([SRC-266](SRC-266-the-test-deployment-runs-on-gcp-and-neon-set-up-b.md)). The suite runs from the owner's machine with one command, and from a GitHub Actions workflow started by hand, which takes its settings from the `live` environment.

## Alternatives considered

- For the machine: Cloud Run with one instance always running (billed for each hour it runs); Fly.io, which the owner first chose and then replaced with GCP; a GKE cluster.
- For HTTPS: Google's HTTPS load balancer with a managed certificate (billed by the hour); plain HTTP.
- For the database: Cloud SQL (billed); PostgreSQL in a container on the same machine.
- For the secrets: Secret Manager, read by the machine at start.
- For the functions: the App for every function, which cannot read a user's Project; a token for every function, which leaves the App out although the owner asked for it.
- For the webhook: the GitHub App's own webhook, whose address and secret are set by hand on the App's page, since the App is registered by hand ([DD-058](DD-058-github-access-uses-apps-registered-by-hand-with-op.md)).
- For the test repository: a GitHub organization of its own, where fine-grained tokens and the App reach the Project and Project changes are sent as webhooks (the owner chose to stay under csillagu); fine-grained tokens only under csillagu, leaving the status field untested.
- For the suite's Project access: a second classic token of its own, apart from the deployment's.
- For the `live` environment: Terraform's outputs only, copied into the environment by hand (the owner chose that Terraform writes them).
- For the tests: against a server the test run starts itself (the owner chose the deployment).

## Rationale

The owner asked for whatever is cheaper or free ([SRC-266](SRC-266-the-test-deployment-runs-on-gcp-and-neon-set-up-b.md)). An `e2-micro` machine is in Google Cloud's free tier and keeps the backend running all the time; Cloud Run, held at one instance, is billed by the hour. Container-Optimized OS runs the published image as it is, with no build on the machine. Caddy obtains and renews a free certificate by itself, where a load balancer is billed by the hour. sslip.io gives the machine a host name without a domain. Neon's free plan holds a small database for nothing, and its pooled and direct addresses fit the tool's two database settings. Instance metadata costs nothing, needs no extra API and no parsing on the machine, and is read only by the project's own users; Secret Manager would add an API, a parser on the machine and its own costs beyond a few secrets.

The App for issues and a token for the Projects status field is the one split that uses both, as the owner asked, and works on a user-owned Project; that token must be classic, as the owner chose. A repository webhook can be created by Terraform, so the webhook secret is generated, given to the tool and set on GitHub in one apply, with nothing copied by hand; the App's webhook cannot be set by Terraform. The suite sets the status field with the deployment's classic token so that the owner keeps one classic token, not two. A short re-check interval stands in for the Project webhooks GitHub does not send for a user's Project.

A run's own project keeps its tasks apart from earlier runs', on a deployment that is not fresh. Removing the repository from the project before deleting its issues keeps the tool from recreating them, as it would recreate a linked issue deleted on GitHub ([FR-136](FR-136-treat-a-linked-issue-deleted-on-github-as-closed.md)).

## Trade-offs

- The machine has 1 GB of memory and a shared CPU: enough for one person's tests, not for real use.
- A change to the settings reaches the machine only when its service or the machine is restarted.
- Each run leaves a project behind in the tool.
- The test cases ask for a fresh deployment; on this one, each test sees what earlier runs left, in projects of their own.
- The suite waits for the re-check after each change it makes to the status field, so those tests take minutes, not seconds.
- The deployment's classic token is given the `project` scope, which writes Projects, although the deployment only reads them.
- The tests of the App's own webhook are not run live: its deliveries are checked by the integration tests only.

## Risks

- The free tier covers one `e2-micro` machine per billing account, in us-west1, us-central1 or us-east1 only, and its terms may change. An external IPv4 address may be billed, a few dollars a month, whether or not the free tier covers the machine.
- A re-check every 2 minutes keeps Neon's compute awake while the machine runs, which can use up the free plan's compute hours within a month. Stopping the machine between runs avoids it.
- Let's Encrypt limits how many certificates are issued per domain, and sslip.io's names are shared by everyone who uses them. A new machine, which needs a new certificate, may be refused one for a while.
- Terraform's state holds every secret in plain text. Lost or shared, it gives them away.
- Terraform needs a GitHub token of the owner's that can write csillagu/cold-seance's environments and secrets and the test repository's webhooks.
- The classic token can do on GitHub what its owner can, on every repository and Project they reach. Kept as an environment secret, it reaches any workflow run in the `live` environment.
- Which fine-grained permission GitHub requires to delete an issue was not found in GitHub's documentation; the clean-up may fail with a token that lacks it.
